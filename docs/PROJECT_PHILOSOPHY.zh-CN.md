# Wuxia Asset Compiler：项目宗旨、理念与边界

> **一句话宗旨：把“参考图里的世界”编译成可控、可复用、可验证、可规模化生产的游戏 3D 资产。**

Wuxia Asset Compiler 不是一个“让 AI 每次临场写几千行 Blender Python”的实验，也不把“每张图都重新跑一次昂贵 Image-to-3D 模型”当作长期生产方式。

我们希望建立的是一种更接近**编译器、程序化资产系统和世界生成器**的生产范式：

```text
参考图 / 理想图 / 美术意图
        ↓
视觉理解与结构分析
        ↓
受约束的 Asset DSL / Scene Spec
        ↓
模板选择 + Style DNA + 参数解析
        ↓
Factory / Macro / Geometry Nodes / Blender API
        ↓
确定性几何与场景生成
        ↓
多视图渲染 + Visual QA
        ↓
参数修复 或 Template Gap
        ↓
几何 / 材质 / 导出验证
        ↓
GLB
        ↓
Godot / 其他游戏引擎
```

---

## 一、为什么要做这个项目

现有“参考图 → 3D”路线通常有两种极端：

1. **每个资产都重新跑图生 3D 模型**：方便，但成本、可编辑性、风格一致性、拓扑质量和游戏管线适配不稳定；
2. **让 LLM 自由生成 Blender 脚本**：灵活，但 token 高、故障率高、难复现、难维护，也很难形成长期资产能力积累。

Wuxia Asset Compiler 选择第三条路：

> **让模型负责“理解与决策”，让稳定代码负责“几何与执行”，让模板库承载长期积累。**

一张参考图不应该只换来一个一次性的 mesh。它应该尽可能沉淀为：

- 一种场景结构；
- 一组房间 / 建筑 / 道具语义；
- 一套可复用 Factory；
- 一批可调参数；
- 一份 Style DNA；
- 一组可自动验收的规则。

这样，同一次工程投入可以生成一族资产，而不是一个孤立资产。

---

## 二、核心信念

### 1. 3D 资产生产可以被视为“编译”

我们不把参考图直接视为 mesh，而把它视为一种**高层意图输入**。

视觉模型先把图像解释成结构化信息，再由编译器把结构化信息转换为确定性 Blender 场景与 GLB。

因此项目中的核心对象不是“某个模型”，而是：

```text
Reference → Spec → Factory → Asset
```

最终目标是让资产生产越来越像：

```text
输入规格 → 编译 → 验证 → 产物
```

而不是：

```text
输入一句 prompt → 希望模型这次发挥正常
```

### 2. LLM / VLM 是解释器与规划器，不是几何真值

模型擅长：

- 理解参考图；
- 识别功能空间；
- 推断空间关系；
- 估计风格和参数；
- 发现视觉差距；
- 提出修复建议；
- 选择已有模板和 Macro。

模型不应该直接拥有：

- 最终几何真值；
- 任意 `bpy` 执行权；
- 拓扑合法性的裁决权；
- GLB 是否可交付的最终判断权。

这些应由确定性代码、测量和验证器负责。

### 3. 模板库才是项目真正积累的“智能”

模型能力会变化，API 会变化，推理成本也会变化；但一个成熟的：

- 屋顶 Factory；
- 山门 Factory；
- 悬崖模块；
- 药柜 Macro；
- 吊锅 Macro；
- 斗拱 / 栏杆 Macro；
- 竹林环境 Macro；

可以长期复用。

因此，每解决一次 `template_gap`，项目就永久增加一种表达能力。

> **我们希望每次失败都让编译器变强，而不是让下一次生成重新从零开始。**

### 4. 风格不是一句 Prompt，而是一套系统

稳定世界观不能只依赖“武侠感”“古风”“旧木”等自然语言。

Style DNA 应逐步固化：

- 比例体系；
- 柱网与建筑模数；
- 屋檐曲率；
- 材料组合；
- 木材老化范围；
- 石材形态；
- 色温关系；
- 道具密度；
- 结构装饰；
- 夜景 / 雾 / 月光语言；
- NPC 活动密度与行为槽位。

同一世界里的多个资产应共享 Style DNA，而不是每张图重新“猜一次风格”。

### 5. Visual QA 的职责是发现差距，不是无限扭参数

视觉模型发现问题后，必须区分：

#### 参数可修
例如：

- 房间偏宽；
- 灯笼太少；
- 道具密度不足；
- 木材太新；
- 悬崖嵌入比例不对。

这些问题允许通过受约束 Patch 修复。

#### 模板能力缺失
例如：

- 当前系统没有高书架；
- 没有吊挂药材；
- 没有人物行为槽位；
- 没有武侠斗拱；
- 没有雾和竹林环境层。

这时系统必须输出 `template_gap`，而不是继续把已有参数推到极端。

> **“做不到”也是一种重要、可行动的输出。**

### 6. 昂贵生成模型可以当老师，不必永远当工人

Tripo、Meshy、Hunyuan3D 或其他专业图生 3D 工具并不是敌人。

它们可以用于：

- 创建第一批高质量教师样本；
- 快速探索设计；
- 为复杂资产提供视觉 / 几何参考；
- 帮助提炼比例和模块语言。

但在固定世界观、固定美术语言、需要批量资产时，我们希望昂贵生成发生在**模板建立阶段**，而不是每个资产都永久依赖一次完整 3D 推理。

理想状态是：

```text
少量昂贵教师样本
        ↓
结构拆解 / 模块化 / 参数化
        ↓
Factory + Style DNA
        ↓
大量低成本可控变体
```

## 三、职责边界

### Vision / LLM 层

负责：

- 参考图解释；
- Scene Graph / 房间功能判断；
- Factory 候选选择；
- 受约束参数估计；
- Visual QA；
- Template Gap 识别。

不负责：

- 任意修改 Blender 场景；
- 自由生成最终几何代码；
- 绕过 Schema；
- 绕过验证器。

### Resolver / Compiler 层

负责：

- Schema 合同；
- 参数范围；
- Factory 所有权；
- 接受 / 拒绝模型建议；
- 模板组合；
- 可重复性；
- Patch 回滚。

### Blender 执行层

负责：

- 几何构造；
- Geometry Nodes；
- 材质与场景；
- Macro 执行；
- 多机位渲染；
- GLB 导出。

### Validation 层

负责最终真值，包括：

- 尺寸与比例；
- transform / pivot；
- mesh 与 triangle budget；
- 非流形 / 退化面；
- 法线；
- UV；
- 材质槽；
- collision；
- GLB 合法性；
- 游戏引擎导入。

视觉模型可以提出“看起来接上了”，但如果几何测量说有缝隙，几何测量优先。

---

## 四、项目的“能力阶梯”

项目应优先沿以下层级积累，而不是不断增加 Agent 自由度：

```text
Primitive
  ↓
Semantic Macro
  ↓
Room / Asset Factory
  ↓
Compound Factory
  ↓
Style DNA
  ↓
World-scale Assembly
```

例如：

```text
Cube / Cylinder
  ↓
TallStorage / HearthFire / HangingRack
  ↓
KitchenRoom / InfirmaryRoom
  ↓
CliffGroundFloor
  ↓
CliffSectCompound
  ↓
完整门派 / 山谷 / 城镇
```

越往上，LLM 应调用越少、语义越清晰的工具。

---

## 五、项目明确“不是什么”

Wuxia Asset Compiler **不是**：

- 一个通用“任何图片一键完美重建 3D”的承诺；
- 摄影测量 / NeRF / Gaussian Splatting 替代品；
- 让 Agent 拥有无限 Blender Python 权限的平台；
- 每个资产重新从零生成的 prompt 集合；
- 对现有武侠 IP 角色、门派、地标或独特美术设计的复制工具；
- 保证无需美术判断、无需工程设计的“全自动魔法按钮”。

它更适合：

- 固定美术风格；
- 独立游戏与中小团队；
- 武侠 / 仙侠 / 东方幻想等模块化世界；
- Godot / Unity / Unreal 等需要稳定游戏资产的生产环境；
- 大量同世界观变体资产。

## 六、成功标准

这个项目是否成功，不只看一张 Blender 渲染图“像不像”。

真正需要同时提升的是：

### 视觉
- 参考图构图与空间关系；
- 风格一致性；
- 语义识别度；
- 生活感 / 道具密度；
- 世界观一致性。

### 工程
- 同 spec + seed 可复现；
- 自动验证通过率；
- GLB 成功率；
- 游戏引擎导入成功率；
- 资产可编辑性；
- Factory 可复用率。

### 经济性
- 单资产 token 消耗；
- 单资产 GPU 依赖；
- 生成时间；
- 人工返工时间；
- 一个 Factory 能覆盖的资产数量。

一个视觉略逊但完全可控、可编辑、可批量生成的资产系统，在生产上可能比一次性的高相似度 mesh 更有价值。

---

## 七、当前开发原则

1. **先做合同，再给 Agent 权限。**
2. **先增加语义 Macro，再增加自由代码。**
3. **参数不能表达的问题必须升级为 Template Gap。**
4. **每个新 Factory 都必须有示例、CI 和 Blender smoke test。**
5. **所有视觉修复必须经过完整 Scene Spec 验证。**
6. **所有游戏产物必须经过几何 / 导出验证。**
7. **参考图用于学习结构和风格，不用于复制受保护 IP。**
8. **第三方代码只在许可证明确兼容时使用。**
9. **世界风格应沉淀为 Style DNA，而不是散落 Prompt。**
10. **每一次工程投入都应增加长期可复用能力。**

---

## 八、长期愿景

短期，我们在验证：

> 一张武侠场景参考图，能否通过“视觉理解 + 有界参数 + Factory + Blender + QA”稳定变成可用 GLB。

中期，我们希望形成：

```text
武侠建筑语法
+ 房间模板库
+ 道具 Macro 库
+ Style DNA
+ 人物行为槽位
+ 环境层
+ 自动 QA
```

长期目标不是生成“一栋楼”。

而是建立一套能够持续编译：

- 山门；
- 门派；
- 客栈；
- 村落；
- 悬崖建筑；
- 山谷道路；
- 桥梁；
- 竹林；
- 药房；
- 厨房；
- 演武场；
- 城镇街区；

的**东方幻想世界资产编译系统**。

最终，我们希望美术人员和设计者表达“世界应该是什么样”，而不是把时间消耗在每个重复构件的机械建模上。

> **让 AI 负责理解世界，让模板保存世界的规律，让 Blender 把规律变成可以运行的空间。**
